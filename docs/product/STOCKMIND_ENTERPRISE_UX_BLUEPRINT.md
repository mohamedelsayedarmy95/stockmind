# STOCKMIND — ENTERPRISE MOBILE UX BLUEPRINT

> **الحالة:** تصميم (Series 08) — **مفيش شاشات اتبنت ولا mock decorative.** هذا الملف بيحدد معمارية المعلومات، التدفقات، الحالات، ومعايير قبول قابلة للقياس.
> **أرقام "أقل من 3 لمسات" والأزمنة المذكورة = أهداف تُقاس في اختبار استخدام، مش حقائق ولا وعود.** ما بتتجاوزش ضمانات الأمان/التكامل.
> المراجع: `STOCKMIND_ORGANIZATION_RBAC_SPEC.md` (الصلاحيات)، `STOCKMIND_MOVEMENT_GOVERNANCE_SPEC.md` (الحالات والتدفقات)، `STOCKMIND_CODE_TO_CAPABILITY_GAP_MATRIX.md` (الموجود فعلاً: M1–M7).

## 2. مبادئ ومعايير قابلة للقياس (تُقاس، مش تُدّعى)

| المبدأ | الهدف القابل للقياس | ملاحظة |
|---|---|---|
| أقل خطوات للمهمة الشائعة | استلام/صرف من الشاشة الرئيسية: **≤ 3 لمسات للوصول لشاشة التأكيد** مع باركود، و**≤ 5** يدوياً (هدف) | الخطوات الإلزامية للأمان (تأكيد صريح، موافقة) **مش بتتحسب كإهدار** |
| صدق الحالة | **صفر** لحظة بتعرض "Confirmed" لشيء لم يؤكده السيرفر؛ كل حالة ليها نص ولون ثابتين (§3) | اختبار آلي على المكوّنات + مراجعة |
| استخدام بيد واحدة | أزرار الإجراء الأساسي في الثلث السفلي؛ لمسات ≥ 48dp | معيار تصميم + مراجعة |
| إمكانية الوصول | تباين نص ≥ 4.5:1 (WCAG AA)، دعم تكبير الخط 200% بدون قص، قارئ الشاشة لكل عنصر تفاعلي | مراجعة + اختبار TalkBack |
| RTL/LTR | كل شاشة تتراجع بـ RTL كاملة؛ **خصائص منطقية** (start/end) مش left/right؛ الأرقام والكميات بعرض ثابت متّسق | يُختبَر على جهاز (عربي) |
| الخصوصية في الواجهة | لا تكلفة/تقييم/أسماء غير مخوّلة في: الشاشة، الكاش، الإشعار، لقطة التطبيقات الأخيرة | RBAC NT-12, NT-43 |

## 4. معمارية المعلومات (illustrative — مش bottom-nav إلزامي)

التنقل بيتبني من `GET /me/capabilities` (RBAC §9). **عنصر لا قدرة له = مش موجود** (مش معطّل بدون شرح). كل شاشة بتتعامل مع: loading / empty / offline / session expired / denied (§8).

### 4.1 Owner / Admin
| القسم | المحتوى | القدرات | ملاحظة |
|---|---|---|---|

| Warehouses | قائمة المخازن + تفاصيل + (لاحقاً) مواقع | `warehouse.*` | إنشاء ← "مين ياخد الصلاحية؟" (CP-4) |
| Team | أعضاء، دعوات، منح نطاق/قدرات، تعليق | `team.*` | عرض أثر الصلاحية قبل الحفظ ("هيشوف 2 مخزن، يقدر يستلم ويصرف، مش هيشوف التكلفة") |

### 4.2 Warehouse Manager (scoped)
نطاقه فقط: **Oversight** (مخازنه)، **Approvals** (ضمن حدوده)، **Operations** (استلام/صرف/جرد/تحويلات)، **Staff** (منح ≤ قدراته)، **Discrepancies**. لا Team على مستوى الشركة، لا Policies (قراءة).

### 4.3 Employee (Operator)
أبسط شكل: **Today** (مهام اليوم والطلبات المعلّقة)، **Scan** (زر أساسي كبير)، **Tasks** (جرد/استلام تحويل لو في)، **My operations** (outbox + حالتي)، **Account** (الحالة، المزامنة، لغة). **لا** كتالوج إداري ولا إعدادات مخازن ولا فريق.

### 4.4 Progressive disclosure
الحقول الاختيارية (مرجع، ملاحظات، مرفقات) مطوية افتراضياً وبتتفتح لما السياسة تطلبها أو المستخدم يضغط؛ الحقول المطلوبة بالسياسة بتظهر من البداية بتعليل ("مطلوب لأن الصرف فوق 50 وحدة").

### 4.5 تبديل الحساب/النطاق
الموجود: scope key (server | company | user) وعزل outbox وكاش لكل حساب (`session-scope.ts`, `account-scope.ts`). المستقبل (multi-org): محوّل منظمات صريح في Account، بيمسح الكاش الحساس ويمنع تطبيق نتيجة على حساب تاني (الضمانات الحالية بتتمدّد).

## 5. الرحلات الخمس الأهم

> **قالب:** نقطة الدخول · نقاط القرار · الحد الأدنى للحقول · العناصر الحساسة للصلاحيات · أونلاين/أوفلاين · نتيجة معلّقة/مؤكدة · فشل/إعادة · RTL/LTR · وصول · **معايير القبول القابلة للقياس**.

### J1 — موظف: صرف بضاعة سريع (Issue) — الأهم
- **الدخول:** Scan (زر رئيسي) أو Today ← "صرف".
- **القرارات:** (1) تحديد المنتج (باركود/بحث) ← (2) الكمية (رقم مباشر؛ السلايدر ثانوي) ← (3) **المستلِم + الغرض** (حسب السياسة؛ آخر قيم مقترحة) ← (4) تأكيد.
- **الحد الأدنى:** منتج، كمية، مخزن (افتراضي = مخزن الموظف الوحيد). المستلِم/الغرض/المرجع **حسب السياسة** وبتظهر مع سبب.
- **حساس للصلاحيات:** المخزن (من grants)، مجرّد وجود "صرف" (`stock.issue`)، حد الكمية، الرصيد المعروض (مؤكد + المعلّق محلياً بجانبه).
- **أونلاين:** تأكيد ← "Confirmed" أو "Waiting for approval" (لو السياسة).
- **أوفلاين:** "Saved on device — not out of stock yet"؛ لو السياسة تتطلب موافقة ← تُحفظ كطلب، **مفيش ترحيل أوفلاين**.
- **فشل/إعادة:** رصيد غير كافٍ 409 ← رسالة واضحة، لا إعادة تلقائية؛ timeout ← نفس المفتاح (موجود).
- **RTL/LTR:** حقل الكمية LTR رقمياً داخل سياق RTL؛ ترتيب الخطوات يتبع الاتجاه.
- **وصول:** حقل الكمية بلوحة رقمية؛ زر التأكيد ≥ 56dp؛ إعلان الحالة بـ live region.
- **قبول:** (أ) ≥ 90% من المختبَرين (n≥6) يكملوا صرفاً بالباركود في **≤ 20 ث** و**≤ 3 لمسات** حتى التأكيد؛ (ب) صفر حالات يفسّر فيها المستخدم "Saved on device" كأنها "Confirmed" في اختبار الفهم؛ (ج) صفر صرف مزدوج عند ضغطتين/إعادة فتح التطبيق (آلي).

### J2 — موظف: استلام توريد (Receive)
- **الدخول:** Scan أو Today ← "استلام".
- **القرارات:** المنتج ← الكمية (+ UOM لو متعدد) ← مرجع المورد/الفاتورة (اختياري إلا لو السياسة) ← تأكيد. **تكرار** "نفس المنتج" سريع (دفعة أصناف).
- **أوفلاين:** مدعوم (outbox موجود).
- **فشل:** مفتاح مكرر/422 ← "حصل تعارض مع طلب سابق" + مراجعة (موجود).
- **قبول:** استلام 5 أصناف متتالية ≤ 90 ث؛ كل صنف يظهر في My operations بحالته الصحيحة؛ صفر ازدواج بعد قطع الشبكة.

### J3 — مدير: صندوق الموافقات (Approval inbox)
- **الدخول:** Approvals (شارة عدد) أو إشعار "في طلبات" (**بلا تفاصيل مالية**).
- **القرارات:** فتح الطلب ← يشوف: مين طلب، إيه، كمية، مخزن، **الرصيد المؤكد الحالي (مع وقته)**، السبب/الغرض، سياسة وإصدارها ← **موافقة / رفض (سبب إلزامي) / طلب توضيح**.
- **حساس:** لا يظهر زر الموافقة لو هو المبادر؛ التكلفة بس لمن يملك `finance`.
- **أونلاين فقط للقرار:** لو الاتصال ضعيف ← "مش هينفع تقرر أوفلاين" + إعادة محاولة (القرار idempotent).
- **نتيجة:** "تمت الموافقة · المنفّذ هيستلم إشعار" / "اترفضت".
- **فشل:** الطلب انتهى/اتلغى/السياسة اتغيرت ← رسالة صريحة وتحديث القائمة.
- **قبول:** قرار واحد ≤ 3 لمسات من الصندوق؛ لا موافقة على طلب منتهي (آلي)؛ موافقتان متزامنتان من مديرين = قرار واحد والتاني بيشوف "اتقرر".

### J4 — Owner: ضم موظف وتحديد نطاقه
- **الدخول:** Team ← دعوة.
- **القرارات:** الاسم/الإيميل ← **profile** (Operator افتراضي) ← **المخازن** (لا افتراضي = لا أحد، يتحدد صراحة) ← خيارات حساسة (التكلفة: افتراضي مقفول) ← **ملخص الأثر** ← إرسال.
- **بعد القبول:** ظهور الموظف في Team؛ تعديل النطاق/القدرات؛ **تعليق/إزالة** بتأكيد (يوضح: الجلسات هتتقفل فوراً، العمليات المعلّقة على جهازه هتتحول لمراجعة).
- **حساس:** كل شيء هنا لـ `team.*`؛ الداعي لا يمنح أكتر من قدراته (NT-34).
- **أوفلاين:** **online فقط.**
- **فشل:** حد الـ plan (seats) ← مسار ترقية صريح (لا خصم)؛ إيميل مسجّل ← رسالة بدون كشف تفاصيل حساب.
- **قبول:** مالك جديد يضم موظف بمخزن واحد في **≤ 2 دقيقة** بدون توثيق؛ بعد السحب، الموظف يفقد الوصول عند **أول طلب** (آلي)؛ لا يشوف أي حاجة من نطاق ما اتمنحش (NT-04/05).

### J5 — تحويل بعهدة: إرسال واستلام (Transfer custody)
- **الدخول:** (المصدر) Operations ← تحويل؛ (الوجهة) Today ← "قادم إليك".
- **القرارات:** المرسِل: الأصناف/الكميات/الوجهة ← **Dispatch** (تأكيد). المستلِم: **عدّ ومطابقة** لكل سطر ← استلام كامل أو **فرق** (كمية + سبب + صورة اختيارية) ← تأكيد.
- **حساس:** مستخدم المصدر لا يرى أرصدة الوجهة؛ المستلِم ≠ المرسِل (مفروض).
- **أوفلاين:** attestations بتتحط في outbox بمفاتيح؛ الحالة النهائية سيرفر؛ **"In transit"** تظهر فقط بعد تأكيد السيرفر للـ dispatch.
- **نتيجة:** "Received" أو "Discrepancy — مفتوح لمراجعة".
- **فشل:** استلامين متزامنين ← واحد بس ينجح؛ التاني "اتستلمت بالفعل".
- **قبول:** فرق في الاستلام بيتسجّل **ولا بيعدّل الرصيد تلقائياً**؛ مجموع on-hand + in-transit ثابت (property test)؛ المستلِم بيكمل استلام 3 أسطر ≤ 60 ث.

### J0 (موجودة) — مراجعة عملية ضايعة بعد restore
Series 07: `outbox-review` (فحص حديث ← تأكيد صريح ← حسم). الاختبارات والجهاز PARTIAL (انظر تقرير S07 §6). **تُوحَّد بصرياً مع معجم الحالات (§3) عند بناء الباقي، ما تتغيّرش وظيفياً.**

## 7. الحالات العامة لكل شاشة

| الحالة | السلوك |
|---|---|
| Loading | هيكل (skeleton) بدل spinner طويل؛ أول مزامنة بتبان "بنحمّل من السيرفر" |
| Empty | سبب + إجراء (مثلاً "ما فيش مخازن مُسنَدة لك — اسأل المدير"؛ **مش** "اعمل مخزن" لموظف) |
| Offline | شريط + "آخر مزامنة"؛ العمليات المسموحة تتحفظ؛ الممنوعة (موافقة/إدارة فريق) تقول لماذا |
| Session expired | `SessionExpiredOverlay` + بصمة؛ **ما يضيعش** المسودة/الـ outbox |
| Denied | رسالة موحّدة؛ بدون كشف وجود المورد |
| Access removed | مسح كاش المخزن + شرح + رجوع للأمان |
| Slow server | "بتتبعت… السيرفر بطيء" (موجود 8 ث) |

## 8. اتجاه الـ design system (مقترح)

1. **Tokens دلالية** فوق الألوان الحالية: `state.confirmed/local/pending-approval/in-transit/discrepancy/offline` + `risk.low/med/high` + `surface.*`؛ كل حالة (§3) ليها token واحد.
2. **نظام نوع (type scale)** بخطين واضحين (لاتيني/عربي) مع قياسات متّسقة؛ الأرقام الكمية بعرض ثابت (tabular).
3. **مكوّنات جديدة محدودة:** `StatusBadge` (من المعجم)، `QuantityField`، `ScopeChip`، `PolicyHint` (يشرح ليه مطلوب)، `ApprovalCard`، `TimelineItem` للـ provenance. **لا مكوّن بدون مستهلك حقيقي.**
4. الأسلوب الداكن "glass" يفضل، مع **وضع تباين عالٍ** ونسخة فاتحة مختبَرة تباينياً.
5. حركة هادئة (haptics + انتقالات قصيرة)؛ Confetti للنجاح العادي **تُراجَع** لأنها بتضرب جدية بيئة العمل (قرار تصميم Q-08).

| المقاييس | زمن المهمة، عدد اللمسات، أخطاء/محاولات، فهم الحالة (اختبار 5 ثوانٍ: "الحاجة دي دخلت المخزون؟")، SUS مختصر |
| العتبات المقترحة (فرضيات للتحقق) | نجاح مهمة ≥ 90%؛ أخطاء فهم الحالة = صفر في الحالات الحرجة؛ SUS ≥ 80 |
| ما لا يُستنتج | عيّنة صغيرة = اتجاه مش إحصاء؛ لا ادّعاء قياس سوق |

## 10. ما لا يُعمل (UX)

- لا mock شاشات decorative ولا "analytics" بدون مصدر بيانات حقيقي (حالياً `dashboardStats` أونلاين = null).
- لا عدّاد "real-time" للأجهزة غير المتصلة، ولا مؤشر "متزامن" إلا لما يكون صحيحاً.
- لا تقييم/تكلفة في أي شاشة/إشعار لمن لا يملك القدرة.
- لا زر يظهر لعملية غير مدعومة/غير مخوّلة.
