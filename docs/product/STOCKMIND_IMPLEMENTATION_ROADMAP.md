# STOCKMIND — IMPLEMENTATION ROADMAP (شرائح رأسية بحسب الاعتماد الفعلي)

> **الحالة:** خطة مقترحة (Series 08، توثيق فقط). **لا تفويض بتنفيذ أي شريحة.** كل شريحة بتحتاج أمر Director منفصل بحدودها وموافقاتها.
> **مفيش جدول زمني بالأشهر.** التقدير بوحدات نسبية (S ≈ أيام قليلة · M ≈ 1–2 أسبوع · L ≈ شهر+) لمهندس واحد مع بوابات الاختبار المعتادة (PG ×3 + mobile + جهاز عند وجود UI) — **فرضيات للتقدير، مش التزامات.** الاعتماد هو اللي بيحدد الترتيب، مش "اكتمال العمود".
> المراجع: `STOCKMIND_ARCHITECTURE_DECISIONS.md` (ADR/Q)، `STOCKMIND_ORGANIZATION_RBAC_SPEC.md` (NT)، `STOCKMIND_MOVEMENT_GOVERNANCE_SPEC.md`، `STOCKMIND_CODE_TO_CAPABILITY_GAP_MATRIX.md` (GM/D).

## 1. خريطة الاعتماد

```
S0 خصوصية التكلفة ─┐
                   ├─► S1 دورة حياة الأعضاء + إبطال فوري ─► S2 قدرات + منح بنطاق + /me/capabilities + CP-4
Milestone R (تشغيلي، موازي، بتفويضات) ─────────────────────────────────────────────┐
                                                                                      │
S2 ─► S3 بيانات الحركة + domain_events + feed v1 ─► S4 سياسات + موافقات (+حجز) ─┬─► S5 جرد
                                                                                ├─► S6 عهدة التحويل
                                                                                └─► S8 مرتجعات + قضايا فروقات
S3 ─► S7 مواقع/lots (بحسب العميل) ─► relocation
S3.. ─► S9 تحليلات/تصدير/API (بعد وجود بيانات حقيقية)
```
**شريحة رأسية** = backend + mobile + اختبارات + توثيق تقدم قيمة قابلة للتشغيل لوحدها (مش "طبقة").

## 2. الشرائح

### S0 — إغلاق تسريب التكلفة (خصوصية) — **الحجم: S** — لا اعتماد — **✅ منفَّذ في Series 09 (على فرع `feature/series09-access-foundation`، لم يُدمج)**
- **ليه الأول:** عيب خصوصية محتمل بالقراءة الثابتة (GM:P2/D1) ومتطلب Director 3.4 صريح. صغير، ومفيش بديل.
- **الخطوات:** (1) **إثبات تشغيلي أولاً:** اختبار PG يسجّل Staff ويطلب `GET /products` على منتج له `costPrice` ويسجّل النتيجة **قبل أي إصلاح** (لو مش مكشوف، الشريحة تتحول لاختبار حماية فقط)؛ (2) `ProductResponseDto` allowlist (نمط `MovementResponseDto` الموجود)؛ (3) قدرة `item.view_cost` (مبدئياً Admin) ؛ (4) إزالة الحقل من الكاش (`Cache-Control: private, max-age=60` على قائمة المنتجات — يتأكد إن مفيش تكلفة تتخزّن) والـ audit والإشعارات.
- **بوابات القبول:** NT-12 أخضر على كل مسارات المنتج (قائمة/تفاصيل/إنشاء/تعديل/صورة/category join)؛ الـ Admin بالقدرة بياخد الحقل؛ لا تغيير في أي رد آخر (اختبار snapshot للعقد)؛ PG ×3 كاملة؛ mobile tsc/Jest؛ لا تغيير migration.
- **المخاطر:** عميل بيعتمد على `costPrice` في الرد (محتمل: mobile بيعرض التكلفة؟ يتحقق) ← إصدار متوافق: القدرة تتمنح للـ Admin، وملاحظة في الـ release notes.

### S1 — دورة حياة الأعضاء + إبطال فوري — **M (backend) + M (Team screen)** — **✅ منفَّذ في Series 09 (backend + Team screen + outbox؛ بدون اختبار جهاز بقرار أمان)**
- **المحتوى:** `members.status`، تعليق/إزالة/إعادة تفعيل، تغيير الدور، `is_owner` (حماية آخر Owner)، `token_version` (إبطال الـ access/refresh فوراً)، audit لكل تغيير، Team screen (قائمة، دعوة، منح مخازن الحالية، تعليق).
- **يعتمد على:** S0 (لا اعتماد تقني، بس ترتيب أولويات).
- **بوابات القبول:** NT-35/36/37/32/33 آلية؛ **بعد التعليق أول طلب بـ token قديم = 401/403** (زمن ≤ طلب واحد)؛ آخر Owner لا يُزال؛ الـ outbox المعلّق لمستخدم معلّق **لا يُنفَّذ** (بيتحوّل لمراجعة عند عودته)؛ جهاز حقيقي: سحب صلاحية أثناء جلسة + تعليق (يتعمل جهازين لو متاحين)؛ PG ×3؛ mobile؛ عربي على الجهاز؛ لا انحدار في `shared-warehouse.pg.spec.ts`.
- **المخاطر:** تغيير دلالات الـ token (migration للـ claim)؛ الجلسة الواحدة لكل مستخدم (D7) تتقيّم هنا.

### S2 — قدرات ومنح بنطاق + `/me/capabilities` + CP-4 — **L** — **✅ منفَّذ في Series 10 (فرع `feature/series10-scoped-access`، لم يُدمج؛ shadow افتراضي، enforce للاختبار المحكوم؛ الجهاز DEFERRED)**
- **المحتوى:** `permission_profiles`، `access_grants` (dual-read مع `warehouse_access`)، `CapabilityGuard` **shadow** ثم تحويل، `GET /me/capabilities`، تنقل الموبايل المتكيّف (ADR-H1)، قاعدة CP-4 (سؤال "مين ياخد الصلاحية" عند إنشاء مخزن)، Manager بنطاق (`warehouse_manager`).
- **بوابات القبول:** shadow mode **صفر اختلاف** على كل الـ suite وعلى سيناريوهات NT-01..43 ذات الصلة؛ NT-04/05/34/39/40/41؛ لا تغيير سلوك لأي عميل حالي (اختبار توافق: كل grant قديم = `operator`)؛ PG ×3؛ جهاز لكل persona (موظف/مدير/مالك).
- **المخاطر:** أكبر شريحة تفويض؛ تقدّم بـ feature flag، وتوقف عند أي اختلاف shadow.

### S3 — بيانات المساءلة + `domain_events` + feed v1 — **L**
- **المحتوى:** حقول الحركة الجديدة nullable (recipient، purpose/reason code، document ref، `captured_at`، UOM)، `domain_events` في نفس الـ transaction + trigger append-only، endpoint قراءة audit/نشاط بصلاحية، **Activity screen للمدير = دمج feeds المخازن المصرّح بها** (ADR-E1)، إشارات FCM بلا بيانات حساسة.
- **بوابات القبول:** كل حركة جديدة ليها `domain_event` في نفس الـ commit (اختبار rollback: لا حدث بدون حركة ولا العكس)؛ UPDATE/DELETE على `domain_events` مستحيل (اختبار)؛ الـ feed **مؤكد فقط** وبـ "آخر مزامنة"؛ NT-15/31/43؛ العملاء القدام يشتغلوا بدون الحقول الجديدة؛ PG ×3؛ جهاز.
- **المخاطر:** حجم الأحداث (غير مقاس)؛ ما يتحطّش hash chain هنا (ADR-G3 لاحقاً).

### S4 — سياسات وموافقات — **L**
- **المحتوى:** `policies` بإصدارات، `operation_requests`، `approval_decisions`، حجز `reserved_quantity`، **تعديل فحص الصرف لـ `base − reserved`**، ترحيل ذرّي بـ `request_id` unique، صندوق موافقات (موبايل)، البداية بـ **التسويات** ثم عتبات الصرف.
- **يعتمد على:** S1 (هوية)، S2 (قدرة `approval.decide` بحدود)، S3 (domain_events).
- **بوابات القبول:** NT-24..29/38؛ **property: صرفان متزامنان لا يتجاوزان المتاح** (مع الحجز والصرف المباشر)؛ المبادر لا يوافق على طلبه؛ لا double posting تحت ضغطتين/timeout/إعادة تشغيل؛ **السيرفر يحوّل straight-through لـ pending لو السياسة اتغيرت** (اختبار توافق مع عميل قديم)؛ الموافقة online فقط (اختبار)؛ PG ×3؛ جهازين (مبادر + معتمد) — **ده أول حد يتطلب جهازين فعلاً**.
- **المخاطر:** تعقيد الحالات والإشعارات؛ **ما يبدأش قبل تحقق من الطلب الحقيقي من شريك تصميم** (§Bible).

### S5 — الجرد (Stocktake) — **M–L** — يعتمد S4 (تسويات بموافقة)
- بوابات: حركة أثناء الجرد بدون overwrite (cut-off)، فصل من عدّ عمّن رحّل، جرد أعمى لا يسرّب النظري، عدّ أوفلاين بإرسال idempotent.

### S6 — عهدة التحويل — **L** — يعتمد S2 (طرفين) + S3 + (S4 لو موافقة)
- بوابات: property الحفظ (on-hand + in-transit ثابت)، استلامان متزامنان = واحد، المرسل ≠ المستلم، فرق ⇒ قضية بلا تعديل تلقائي، مستخدم المصدر لا يرى أرصدة الوجهة (NT-19..22)، الوضع الفوري يفضل شغّال.

### S7 — مواقع/Lots/Serials (حسب ICP) — **L** — يعتمد S3
- **لا يبدأ إلا لو شريك تصميم طالب أصناف lot/serial** (FMCG ← lots/تواريخ صلاحية؛ قطع الغيار ← مواقع/serials). بوابات: مجموع positions = رصيد المخزن (property)، relocate لا يغيّر الكمية، FEFO/FIFO على السيرفر بنفس نتايج المحلي (اختبار تكافؤ).

### S8 — مرتجعات وقضايا فروقات — **M** — يعتمد S4/S6.

### S9 — تحليلات وتصدير وتكاملات — **L** — بعد وجود بيانات حقيقية
- تحليلات **read models** صادقة (لا أرقام بدون مصدر)، تصدير/استيراد CSV أولاً، ثم API keys/webhooks (`service_accounts`) — **بعد** استقرار domain_events. **Vision/OCR/forecasting = spikes بحثية قابلة للإلغاء** بمعايير دقة مقاسة قبل أي وعد.

## 3. Milestone R — الجاهزية التشغيلية (موازٍ، مش ميزة)

**الهدف:** تقفل شروط Production اللي الكود وحده مايقفلهاش. **كل بند بتفويض صريح من الـ Director**، وبيئة **غير إنتاجية** (فرع Neon مؤقت لو وافقت).

## 6. القرار: **الـ milestone التنفيذي التالي (واحد فقط)**

### **Series 09 — Access Foundation, Part 1 (S0 + S1)**

**السبب:** أعلى قيمة مقابل مخاطرة: (أ) يقفل عيب خصوصية مالي محتمل، (ب) يدّي المالك أول مرة قدرة إزالة موظف سابق/تغيير دور (مفيش حاجة من الحوكمة، ولا من الموافقات، ولا من أي customer rollout تتحرك بدونها)، (ج) نطاق محدود وبنفس أنماط الكود الحالي (allowlist DTO، migration additive، `down()` fail-closed، اختبارات PG)، (د) مفيش تفويض خارجي مطلوب.
**النطاق:** S0 + S1 (backend + Team screen بسيط). **خارج النطاق:** profiles/grants الجديدة (S2)، الموافقات، أي تغيير ledger.
**الشروط المسبقة (الاعتماد الدقيق):**
1. أمر Director صريح بالنطاق ده (S0+S1) — ومعه قرارات **Q-03** (Owner/نقل ملكية) و**Q-02** (معنى Manager: يفضل كما هو في هذه المرحلة).
2. فرع جديد من `design/series08-enterprise-blueprint` (بيحتوي كل كود Series 07 كما هو + حزمة التوثيق، والفرق عن `feature/series07-recovery-integrity` توثيق فقط — يتحقق بـ `git diff --name-only dc4ff4d HEAD`). ده بيخلّي الـ bridge والـ master والـ docs/product في مكان واحد.
3. PostgreSQL المحلي المؤقت (موجود)؛ جهاز Huawei + الـ Director للبصمة؛ **جهاز ثانٍ اختياري** للتحقق من D7.
4. **صفر Production/Neon.**
**بوابات القبول (ملخص):** إثبات تشغيلي لتسريب التكلفة قبل/بعد؛ NT-12/32/33/35/36/37؛ إبطال فوري بعد التعليق؛ حماية آخر Owner؛ توافق عملاء حاليين؛ PG ×3 على قواعد جديدة؛ mobile tsc/Jest؛ جهاز (تعليق أثناء جلسة، سحب صلاحية، عربي)؛ تقرير + bridge.
**بالتوازي (غير كودي):** **Milestone R** يبدأ بقرارك على R1/R2/R3 (بيئة غير إنتاجية) — بيقفل أغلب عوائق Production المتبقية بدون ما يكلّف كود.
